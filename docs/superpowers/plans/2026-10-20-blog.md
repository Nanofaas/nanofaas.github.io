# NanoFaaS Blog Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A blog on nanofaas.github.io: shareable posts at `/blog/<slug>/`, an index at `/blog/`, the latest three posts on the landing page, a hidden `/blog/new/` page that opens GitHub's editor pre-filled, and a first post announcing NanoFaaS 0.23.0.

**Architecture:** Native Jekyll posts in `_posts/`, given `layout: post` and `permalink: /blog/:title/` by `_config.yml` defaults. Two includes (`post-card.html`, `share.html`) are shared by the landing section, the blog index and the post layout. `/blog/new/` is a static form whose inline JS builds a GitHub "new file" URL. `scripts/check.sh` gains a second Jekyll build with no posts to prove the empty state.

**Tech Stack:** Jekyll 3.10 (`github-pages` gem, Liquid 4), kramdown + Rouge, `jekyll-seo-tag`, plain CSS, small inline JS, Docker `ruby:3.3` for builds. Figures for the first post: LuaLaTeX + TikZ, `pdftocairo` for SVG/PNG.

**Spec:** `docs/superpowers/specs/2026-10-20-blog-design.md`

## What "release candidate" means here

It describes the scope, not the operating model. NanoFaaS still runs as a single control-plane instance, keeps executions and queues in memory (the function catalog is persisted to a file) and has no authentication. Put it behind your own access control, and expect in-flight executions to be lost when the control plane restarts.

## A third deployment backend: rootless containerd

`containerd-deployment-provider` runs functions on rootless containerd with crun, next to the Kubernetes and Docker-compatible providers ([#212](https://github.com/Nanofaas/nanofaas/pull/212)). It applies CPU and memory limits, waits for readiness, scales replicas, adopts running replicas after a control-plane restart and retries cleanup. Registry hosts can be configured for mirrors, plain-HTTP registries and custom CAs ([#251](https://github.com/Nanofaas/nanofaas/pull/251)). Like the other providers it is picked at build time, and the three are mutually exclusive. Setup is in [`docs/deployment-containerd.md`](https://github.com/Nanofaas/nanofaas/blob/v0.23.0/docs/deployment-containerd.md).

## Schedulers you can switch at runtime

Invocations now go through one scheduler engine with two strategies: `per-function` queues and a `shared-queue` ([#214](https://github.com/Nanofaas/nanofaas/pull/214)). `nanofaas.scheduler.strategy` picks one at startup, and an unknown id refuses to start instead of falling back. With the runtime-config admin API enabled, you can switch strategy on a live control plane:

```bash
curl -fsS -X PATCH http://localhost:8080/v1/admin/runtime-config/scheduler \
  -H 'Content-Type: application/json' \
  -d '{"expectedRevision":0,"values":{"strategy":"shared-queue"}}'
```

The admin API stays off by default and has no authentication. Retries now honour `Retry-After` instead of being republished at once, and a newly registered deployment is held until it is first ready ([#217](https://github.com/Nanofaas/nanofaas/pull/217)).

## Recipes v2

A `schemaVersion: 2` recipe can express the builds NanoLab used to script on the host; version 1 recipes keep working ([#219](https://github.com/Nanofaas/nanofaas/pull/219), [#220](https://github.com/Nanofaas/nanofaas/pull/220), [#222](https://github.com/Nanofaas/nanofaas/pull/222)).

- **Native options per component:** optimisation level, garbage collector and monitoring.
- **Native builds in a container:** with `builder: container` a native component compiles inside the same GraalVM builder the release uses. The host needs only Docker with BuildKit, so native images now build on macOS and Windows too.
- **Multi-architecture images with provenance:** `registry.platforms` builds every image with `docker buildx`, and `provenance: true` attaches BuildKit provenance.

```yaml
schemaVersion: 2
name: demo
registry:
  repository: ghcr.io/my-org
  tag: "1.0.0"
  platforms: [linux/amd64, linux/arm64]
  provenance: true
controlPlane:
  modules: [async-queue, container-deployment-provider, build-metadata]
  build:
    mode: native
    builder: container
    native: {optimization: s}
```

Native builds also evaluate Spring AOT conditions with the recipe's configuration, so a JVM and a native control plane built from the same recipe select the same components ([#224](https://github.com/Nanofaas/nanofaas/pull/224)).

## A Rust SDK and smaller function images

Functions can now be written in Rust. The SDK implements the same runtime contract as the others, `fn-init` has a Rust template, and the four reference functions ship in Rust too. That makes Java, Python, Go, JavaScript and Rust, plus Bash examples.

Function images got smaller:

| Language | Before | Now |
|---|---|---|
| Go | ~21.5 MB on Alpine | ~8.9 MB, static binary on `scratch` |
| Python (`word-stats`) | 156.6 MB on `slim` | 72.8 MB on Alpine, precompiled bytecode |
| JavaScript | 117.5 MB on Node 20 | 108.9 MB on Node 24 (Alpine) |

## In beta: P2P discovery, forecasting and one-shot offload

Three additions are excluded from the default build and inert until enabled. Expect their configuration and APIs to change.

- **`p2p-discovery`** finds other NanoFaaS nodes, measures latency and Vivaldi coordinates, picks active neighbours and exchanges messages with them ([#234](https://github.com/Nanofaas/nanofaas/pull/234)). Neighbours can also share registered functions, image inventories and resource observations ([#241](https://github.com/Nanofaas/nanofaas/pull/241)). Every node knows every other node, which fits tens to a few hundred nodes. See its [README](https://github.com/Nanofaas/nanofaas/blob/v0.23.0/platform/modules/p2p-discovery/README.md).
- **`forecasting`** estimates each function's future arrival rate, with an EWMA over observed requests or from a supplied trace ([docs](https://github.com/Nanofaas/nanofaas/blob/v0.23.0/docs/forecasting.md)).
- **One-shot offload**, a new mode of the `offload` module, uses both: nodes agree over P2P which replicas each one prepares and whether a request runs locally, on a neighbour or in the cloud ([#244](https://github.com/Nanofaas/nanofaas/pull/244), [docs](https://github.com/Nanofaas/nanofaas/blob/v0.23.0/docs/one-shot.md)).

## Hardening

- Release checks now block on any failed, cancelled or skipped job and on new SpotBugs findings ([#243](https://github.com/Nanofaas/nanofaas/pull/243)).
- SonarQube findings went from 538 to 0 across Java, Python, Go, JavaScript and Rust ([#215](https://github.com/Nanofaas/nanofaas/pull/215)).
- Fixes for native builds (CLI configuration contexts, AWT libraries in the QR function), for restarting with persisted resource settings, and for read timeouts on external functions, now reported as `EXTERNAL_TIMEOUT`.
- `/actuator/info` reports the effective execution retention ([#233](https://github.com/Nanofaas/nanofaas/pull/233)).

## Upgrade notes

- Python projects need Python 3.12 or newer.
- The JavaScript SDK and functions need Node 24.
- When a synchronous caller's wait times out, the response is now HTTP 408 with the execution id and `status=timeout`. The execution keeps running and can still be polled.
- Function-management errors share one JSON shape: `{error, message, details?}`.
- The Helm chart runs exactly one control plane and upgrades it with the `Recreate` strategy.
